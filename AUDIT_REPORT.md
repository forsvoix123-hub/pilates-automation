# Аудит HARMONY FAMILY

**Дата аудита** — 25 ноября 2026 года.

Аудит охватил клиентское приложение, CRM, серверные действия Next.js, миграции Supabase и тесты PostgreSQL. Дизайн и согласованные правила записи и списания сохранены. RLS оставлен включённым. Данные в размещённом Supabase не менялись.

## Найденные и исправленные ошибки

| Обнаружено | Исправлено |
| --- | --- |
| Длинные списки могли обрезаться лимитом строк PostgREST. Раздельное чтение занятий, записей и абонементов могло объединить данные до и после одной операции. | Клиентское приложение и CRM загружают единый снимок через RPC `load_studio_snapshot`. Функция возвращает один JSON-объект, читает данные в рамках одного снимка PostgreSQL и применяет права вызывающего пользователя и действующие политики RLS. |
| Фоновое обновление могло скрыть сообщение об ошибке до того, как пользователь его прочитает. Ошибка смены статуса могла предложить проверить поля формы, даже если действие выполнялось кнопкой. | Ошибки действий сохраняются при фоновом обновлении. Для неудачного изменения статуса добавлено сообщение с указанием проверить занятие и остаток абонемента. |
| В производственном режиме cookie сессии не имела флага `Secure`. | Настройки сессии объединены для серверного клиента и прокси. В production cookie получает `Secure` и используется через HTTPS. Конфигурация Supabase ограничена серверным импортом. |
| Команды отдельной проверки TypeScript и запуска линтера отсутствовали. | Добавлены `typecheck` и `lint`. Исправлены замечания к навигации Next.js, начальной загрузке данных и экспорту конфигурации PostCSS. |

## Проверенные сценарии

| Область | Результат |
| --- | --- |
| Групповая запись | Подходящий действующий абонемент со свободным остатком даёт `confirmed` и резерв одного занятия. Без подходящего абонемента создаётся `pending`. При исчерпанном остатке подходящего абонемента сервер отклоняет новую запись. |
| Абонементы | Направление должно совпадать с направлением услуги. Проверяются текущая дата и дата занятия в часовом поясе студии `Europe/Belgrade`. Границы периода включены. Если подходят несколько абонементов, используется доступный абонемент с ближайшей датой окончания. |
| Статусы и доступность | Проверены ожидание, подтверждение, отклонение, отмена клиентом и администратором, отмена занятия и посещение. После отклонения или отмены возможна новая запись на доступное будущее занятие. Активная запись блокирует дубль. Запись закрывается в момент начала занятия. |
| Резерв и списание | Подтверждение резервирует занятие. Отмена освобождает резерв. Посещение уменьшает остаток и резерв на единицу. Доступное количество равно остатку за вычетом резерва. Повторная отметка посещения и записи без привязанного абонемента не меняют его показатели. |
| Автоматическое подтверждение | При сохранении подходящего абонемента в CRM будущие групповые заявки подтверждаются по времени занятия в пределах свободного остатка. Сохраняются UUID заявок и число занятых мест. Индивидуальные, отменённые и отклонённые записи пропускаются. |
| CRM и клиентское приложение | Проверены подписи и доступность кнопок, в том числе повторная запись после отмены. Баланс в CRM и личном кабинете строится из одних и тех же полей. Выполнена локальная HTTP-проверка перенаправления на вход для `/` и `/admin` без сессии. Форма входа вернула HTTP 200. |
| RLS и права | На локальной базе проверены отдельные роли клиента и администратора. Клиенту недоступны данные CRM, чужие записи и абонементы. Попытки сменить чужой статус, выполнить запись от имени другого клиента и напрямую изменить закрытые поля отклоняются. |
| Конкурентная запись | На локальном PostgreSQL два клиента с разными подключениями претендовали на последнее место. Второе подключение дождалось блокировки и получило отказ. Осталась одна запись при одном занятом месте. |

## Что осталось проверить вручную

Миграция `00800` не применялась к размещённому Supabase. Вход под реальными тестовыми аккаунтами и ответ нового RPC через размещённый PostgREST не проверены. Проверка двух одновременных подключений выполнена на локальном PostgreSQL.

1. В Supabase SQL Editor выполни [миграцию 00800](supabase/migrations/20261125000800_harmony_consistent_snapshot.sql) после `00700`. Повторно запускать `seed.sql` не требуется.
2. Войди под администратором и клиентом в отдельных браузерных сессиях. Убедись, что клиент видит свои записи и абонементы, а вход на `/admin` доступен администратору.
3. Проверь подтверждение, отклонение и повторную запись, затем отмену и отметку посещения. Сверь в CRM и клиентском приложении статус, свободные места, остаток, резерв и доступное количество. Проверь, что сообщение об ошибке остаётся видимым при очередном фоновом обновлении.
4. Если приложение запущено по HTTPS в production, проверь вход и выход и убедись в инструментах браузера, что cookie сессии имеет флаги `Secure` и `HttpOnly`.

## Решения по бизнес-правилам после аудита

Согласованные правила реализованы в [миграции 00900](supabase/migrations/20261125000900_harmony_cancellation_and_refunds.sql) и подключены к CRM и клиентскому приложению.

| Правило | Реализация |
| --- | --- |
| Подтверждение заявки и посещение | Администратор может подтвердить ранее созданную заявку до окончания занятия, включая время после начала. Самостоятельная запись закрывается с начала занятия. Посещение можно отметить с начала занятия. Окончание вычисляется по времени начала и длительности услуги. |
| Предварительная запись по абонементу | Сверяются направление, дата занятия в часовом поясе студии и доступный остаток. Абонемент может начать действовать позже текущей даты. То же правило применяется при пересмотре будущих групповых заявок во время выдачи или изменения абонемента. |
| Бесплатная отмена | В CRM → Расписание задаётся общий срок в целых часах. По умолчанию 12 часов. Отмена точно на границе считается бесплатной. Для расчёта используется настройка на момент отмены. |
| Поздняя отмена и неявка | Для подтверждённой записи с абонементом резерв освобождается, остаток уменьшается на одно занятие. Администратор отмечает неявку после окончания занятия. Записи без привязанного абонемента не меняют его баланс. |
| Отмена студией | Резервы по действующим записям освобождаются, ранее списанные занятия возвращаются, если по ним ещё не было возврата. История посещений и неявок сохраняется. |
| Исключение администратора | Для списанной записи доступен однократный возврат с обязательной причиной. Система сохраняет дату, причину и источник возврата. Списание и возврат выполняются атомарно. Если ручная корректировка остатка уже довела его до исходного лимита абонемента, возврат останавливается с сообщением о превышении лимита. При таком конфликте отмена занятия студией тоже откатывается целиком. |

RLS сохраняется. Клиент может читать настройку срока отмены, а менять её и делать ручные возвраты может администратор. Исторические посещения, уже обработанные миграцией `00700`, получают отметку списания без повторного уменьшения остатка.
